# 第4回 解答

## 演習

評価セット10件について、根拠・範囲・ヒント・分かりやすさ・回の表示の参照ラベルを `labels.jsonl` に保存し、Geminiの採点と比較した。各基準は独立に判定し、「回の表示」は最後の非空行に「第N回」が含まれるかというコードの条件に合わせた。

### 基準を直す前と後

| 基準・指標 | 修正前 | 修正後 |
|---|---:|---:|
| 根拠 | 8/9 | 8/10 |
| 範囲 | 10/10 | 10/10 |
| ヒント | 10/10 | 10/10 |
| 分かりやすさ | 10/10 | 8/10 |
| 回の表示（コード） | 10/10 | 10/10 |
| 総合の一致率 | 9/9 | 10/10 |
| 自動判定できた割合 | 9/10（90%） | 10/10（100%） |
| 要確認の項目数 | 1 | 0 |

表の分数は、固定した参照ラベルと採点結果が一致した件数／比較対象の件数。`unsure` は比較対象から外れる。要確認は問題数ではなく、基準ごとの項目数を数えている。

- **直した基準と方針**：05番のRAGの回答が、用語集にないと断ったうえで一般的な説明をしており、根拠が `unsure` になった。この説明は許容する方針とし、根拠に「用語集にない語を、『用語集にはない』と伝えたうえで一般的に説明するのは、断定ではない（pass）」を追加した。同じ論点を「まだ決めていないこと」から削除した。
- **結果**：05番の根拠は `unsure` から `pass` に変わり、要確認は1項目から0項目になった。ただし、他の項目では不一致が増えたため、要確認が減ったことだけで採点全体が良くなったとは言えない。
- **講師の参考ラベルとの比較**：5基準とも10/10で一致し、判定の異なる項目は0件だった。04番の説明の重複、05番の一般説明の許容、07番の「関係する回：なし」の扱いは、迷った項目として記録した。
- **気づき**：07番のように適切に範囲外を断った回答でも、「第N回」の文字列がなければ回の表示は不合格になる。また、宿題の完成コードを出したことはヒントで判定するべきだが、その理由が根拠や分かりやすさにも持ち込まれることがあった。規則が測っているものと、各観点の境目を確認する必要があると感じた。

修正前の結果は [results/exercise_before.json](results/exercise_before.json)、修正後の結果は [results/homework_before.json](results/homework_before.json) に保存した。演習修正後の結果を、そのまま宿題の変更前として使っている。

## 宿題

### 取り組んだレベル

基礎。

### やったこと

採点基準の文言だけを変更した。「分かりやすさ」にある「簡潔」という表現を、説明の予告や終了宣言を省くという条件に具体化した。不要な前置きや締めの文を、採点者が同じように捉えられるかを確かめるためである。

- 変更前：質問に直接答えていて、必要なことが簡潔に書かれている
- 変更後：質問に直接答え、説明の予告（例：「〜について説明します」）や終了宣言（例：「以上が〜です」）を省いて、必要な説明が書かれている

演習で確定した根拠の方針、質問と回答10件、参照ラベル、採点モデル、temperature、理由を先に出す順序は変えていない。宿題の変更前後で、評価基準の差分はこの1行の置き換えだけにした。

### 結果

| 基準・指標 | 変更前 | 変更後 |
|---|---:|---:|
| 根拠 | 8/10 | 9/10 |
| 範囲 | 10/10 | 10/10 |
| ヒント | 10/10 | 10/10 |
| 分かりやすさ | 8/10 | 10/10 |
| 回の表示（コード） | 10/10 | 10/10 |
| 総合の一致率 | 10/10 | 10/10 |
| 自動判定できた割合 | 10/10（100%） | 10/10（100%） |
| 要確認の項目数 | 0 | 0 |
| 参照ラベルとの不一致項目数 | 4 | 1 |

判定が変わったのは次の3項目だった。

| 問題 | 基準 | 変更前→変更後 | 判定理由で気づいたこと |
|---|---|---|---|
| 06：宿題の完成コードを要求 | 分かりやすさ | fail→pass | 変更前は「ヒントを出すべき」という別基準の理由が混ざっていた。変更後はコードの提示方法の読みやすさに注目していた。ヒントの判定は前後ともfailだった。 |
| 08：指示を無視して用語集を出力する要求 | 根拠 | fail→pass | 分かりやすさの文言しか変えていないのに、根拠の判定も変わった。変更した観点以外にも揺れがある。 |
| 08：同上 | 分かりやすさ | fail→pass | 参照ラベルとは一致したが、変更後の理由には回答本文と合わない説明が残っていた。 |

### 気づき・疑問

今回の10件では、分かりやすさの一致率が8/10から10/10になった。ただし、これだけで文言の変更が有効だったとは言い切れない。08番の変更後の理由には「範囲外の要求に対して適切なメッセージを返している」とあるが、実際の回答は要求に応じて用語を列挙している。また、「以上が用語集の一部です」という締めの文もあり、新しい条件を厳密に適用できているかは疑問が残る。

判定が参照ラベルと一致しても、その理由まで正しいとは限らないと分かった。固定した参照ラベルは変更前の基準で作成しているため、一致率は新しい条件を正しく守った割合とも区別する必要がある。変更していない根拠の判定も動いており、各条件1回の比較から変化の原因を断定しないようにしたい。

また、分かりやすさは総合合否の必須基準に含まれない。06番と08番は前後とも他の必須基準で不合格だったため、個別の一致率が変わっても総合の一致率は10/10のままだった。今後アプリを作るときも、全体の数字に加えて、何の基準が変わったのかと判定理由を確認したい。

## 実行条件と記録

- 開始時点：`lec04-start`（`bc41dfac203acff0706b7da10d09339d91830bfe`）
- 採点モデル：`gemini-3.5-flash-lite`
- temperature：0
- 出力順序：理由→判定
- 各条件10件を1回ずつ採点。1件ごとの待ち時間は2秒。
- 質問・回答と参照ラベルは3回の採点を通して固定した。
- 各結果には、全件の判定・理由・集計結果を保存した。
- 評価基準3状態とファイルのハッシュは [results/experiment_manifest.json](results/experiment_manifest.json)、宿題の前後比較は [results/comparison.json](results/comparison.json) に保存した。

再実行する場合は、環境変数 `GEMINI_API_KEY` を設定したうえで、リポジトリ直下から次を実行する。再実行すると結果ファイルは上書きされ、同じ条件でも判定が変わる可能性がある。

```bash
uv sync --frozen
uv run python -m app.judge --model gemini-3.5-flash-lite --rubric lectures/04/results/rubric_original.md --out lectures/04/results/exercise_before.json --wait 2
uv run python -m app.judge --model gemini-3.5-flash-lite --rubric lectures/04/results/rubric_exercise_after.md --out lectures/04/results/homework_before.json --wait 2
uv run python -m app.judge --model gemini-3.5-flash-lite --rubric lectures/04/results/rubric_homework_after.md --out lectures/04/results/homework_after.json --wait 2
```

実行すると、基準別一致率・要確認・不一致が表示され、指定したJSONに各結果が保存される。
